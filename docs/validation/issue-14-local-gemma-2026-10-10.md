# Issue #14 本机 Gemma 4 验证

验证时间：2026-10-10T00:42:45.065291+08:00（Asia/Shanghai）

使用 LM Studio 中已加载的 `gemma-4-26b-a4b-it`，量化 `Q2_K_XL`，上下文 **8192 token**。所有模型响应均来自本机 HTTP 服务，所有 Read/Edit/Bash 均执行真实工具。观测包装器只记录计数并调用原实现，没有伪造响应或工具结果。

## 修复前后对照

在同一临时工作区创建 13 个文件，每个文件含 11,000 个空格作为填充、随机校验标记及下一个文件名。每轮只读一个完整文件，最后返回全部标记。两组都使用相同的真实主代理进度指令。默认运行预算 **1,000,000** 未上调。

| 版本 | 结果 | 真实累计输入与输出 token | 内部预算计量 | 完成的读取 |
| --- | --- | ---: | ---: | ---: |
| 原版 `4b8b4c4` | 第 14 次请求发送前被预算阻止，没有最终结果 | 50,797 | 952,503 | 13 |
| 当前修复版 | 14 轮完成，全部随机标记正确 | 59,049 | 279,215 | 13 |

原版错误：`run token budget cannot cover another provider request`。原版运行 68.29 秒；修复版运行 62.17 秒。

修复版最后一次真实请求的输入为 7,484 token，输出为 677 token，能够放入当前 8192-token 上下文。

这证明了原版会在真实 provider 累计使用量远低于预算时被字节计量提前阻止。修复后的内部预算仍含本地估算下限，不等于实际 token 使用量。空白填充压缩率较高，所以这个实验中的估算仍明显偏保守。

## 真实工具与错误路径

- Read → Edit → Bash：通过，独立核对了文件内容、Bash 成功标记、修改恢复记录，并完成恢复确认。4 轮，3,623 个 provider 报告 token。
- 后续只读委派：通过，真实 Read 读取并正确返回文件内容。2 轮，1,142 个 provider 报告 token。
- 真实 MCP stdio 错误路径：通过。仅在一次性测试服务器中将预算设为 3,000，模型实际调用一次 Read 后，下一请求被阻止。工具结果及日志均包含 `run token budget cannot cover another provider request`。产品默认预算未改变。

## 观察到的模型限制

首次不加主代理继续指令时，两组都在读取 6–7 个文件后提前返回空响应，当时预算未耗尽。这是另一个模型/响应行为限制，未被这次预算修复解决。成功的 14 轮对照包含真实主代理进度指令，不能据此声称模型在所有无引导长任务中都能自主完成。

文件采用人工空白填充，以便在本机 8192-token 上下文中验证 JSON 字节计量；本次没有验收多份自然语言或代码大文件超过模型上下文的场景。
